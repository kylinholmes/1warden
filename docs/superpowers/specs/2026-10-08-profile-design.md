# Encrypted account Profile

Follow-up: [User details and encrypted account metadata](../../account-details.md)
extends this design with preferences, device history and manual avatar cropping.
The user now authorizes automatic device registration to create the special note
after verified unlock; display-name/avatar and preference edits remain explicit.

The user requests a special vault record as their Profile, with a Base64 avatar and display name in its encrypted notes. After unlock, decrypt and cache the presentation locally. The ongoing 1Password-inspired palette refresh remains independent.

Use an ordinary secure note marked by encrypted custom field `1warden:record-type=user-profile`. Notes are a versioned JSON object (`schema: 1warden.profile`, `version: 1`, `displayName`, `avatarDataUrl`), retaining unknown properties during edits. Only explicit saves create/update records. Profile notes are hidden from ordinary 1Warden browse/search/reports; other Bitwarden clients can see the secure note. Newest active marked record wins deterministically; never delete duplicates. Invalid/newer schema prevents overwrite. Saved revisions prevent stale editor writes.

Compress uploaded raster avatars locally to a square JPEG, up to 128 px, adapt quality/dimensions to <= 5600 data-URL characters. Cap JSON UTF-8 size at 7000 bytes to fit Vaultwarden's default encrypted-note limit. Reject unsupported image inputs and oversize data before writes.

Only validated displayName and avatarDataUrl are persistently cached in host storage, partitioned by server/account. This is an explicit user-requested exception for presentation preferences to the existing vault-plaintext invariant; passwords, arbitrary notes, keys and future unknown profile fields never enter this cache. Lock retains presentation; logout removes it, and delayed storage writes cannot resurrect it. A server deletion clears stale profile after completed sync. Storage failure must not turn a successful server save into failure.

Settings > Account edits Profile. Sidebar and lock screen use cached name/avatar, with email/initial fallback. This display name does not change server login email. Only a successful authoritative sync establishes profile readiness. Initial/failed sync cannot clear cached presentation or create a duplicate Profile; legacy restored sessions with unknown sync readiness require reauthentication before editing.

The sidebar header is the user's avatar and display name, replacing the product logo and separate email footer. Its secondary menu contains the current identity, remembered other accounts, Add Account, Update Avatar/Profile, Settings and Logout (登出). Email and backend remain visible inside the menu so same-email accounts on different servers are distinguishable. Long menus scroll within the viewport and mobile safe area; keyboard navigation, Escape and error recovery are supported.

The user explicitly selected working multi-account switching in this iteration. Identity is the canonical backend URL plus normalized email. The user subsequently revised the switching requirement: already unlocked accounts switch directly without another password. Each identity retains its own verified session in memory; selecting another identity cancels pending secret operations and replaces the visible account without mixing keys, records or caches. Browser sessions live only in trusted storage.session and retain each original absolute 15-minute expiry; native sessions retain independent in-memory clients and timers. Locked, logged-out or expired targets require authentication against their own backend. Lock/logout affect only the selected identity. Add Account opens an empty connection form with a visible Back button returning to the original account, including after failed requests or closing/reopening the popup. Drafts record only public origin identity, fields and errors; preparing the draft precedes publishing the empty application snapshot. Failed/unsubmitted connection drafts preserve public fields and errors but never the master password. Remembered identities are selected only by the user.

The shared light/dark palette uses blue primary controls, pale blue/light paper surfaces or navy dark surfaces, and violet/teal/rose/amber semantic icons. Existing narrow full-window cards and right-slide motion remain. Tests use synthetic records and the explicitly supplied local test account, never the user's personal vault; temporary test records and disposable backend data are cleaned up.

The product is now named **1Warden**. Existing storage, protocol, bundle identifiers and encrypted Profile schema/marker stay compatible with installed 1Warden data. The avatar menu exposes only 登出; automatic locking, keyboard/native lock commands and expiry remain available.
